# Платформа инструментов — гайд разработчика

`aitc` — это каркас, в который **ты подключаешь две вещи**: свои инструменты и свою
модель. Больше ничего реализовывать не нужно.

## 1. Подключить инструмент

Инструмент = имя + описание + подсказка по аргументам + колбэк. Колбэк получает
разобранный объект аргументов (`nlohmann::json`) и возвращает текстовый результат,
который уйдёт обратно в модель.

```cpp
aitc::ToolRegistry reg;

reg.add(
    "weather",                                   // имя (его зовёт модель)
    "Текущая погода в городе",                    // описание (попадёт в системный промпт)
    R"({"city": "<название>"})",                  // подсказка по аргументам (для промпта)
    [](const nlohmann::json& args) -> std::string {
        const std::string city = args.value("city", "");
        return lookupWeather(city);              // твоя логика
    });
```

Можно цепочкой:

```cpp
reg.add("add", "Сложить два числа", R"({"a":<num>,"b":<num>})",
        [](const nlohmann::json& a){ return std::to_string(a.value("a",0.0)+a.value("b",0.0)); })
   .add("now", "Текущее время", "",
        [](const nlohmann::json&){ return currentTimeIso(); });
```

**Правила хорошего инструмента**
- Результат — **компактный текст**: он становится частью следующего промпта.
- Аргументы читай терпимо: `args.value("ключ", дефолт)` — модель может пропустить поле.
- Не бросай наружу: реестр ловит исключения и отдаёт модели читаемое сообщение, но
  лучше вернуть осмысленную строку («Город не найден»), чем кидать.
- Имя — стабильный идентификатор (его модель видит в промпте и зовёт буквально).

## 2. Подключить модель

Реализуй `IGenerator` — единственный метод `generate(prompt) -> completion`:

```cpp
class LlamaGenerator : public aitc::IGenerator {
public:
    explicit LlamaGenerator(const std::string& gguf) { /* загрузка модели */ }
    std::string generate(const std::string& prompt) override {
        return runLlama(prompt);                 // твой инференс
    }
};
```

Подойдёт что угодно: llama.cpp, локальный HTTP-эндпойнт (Ollama/llama-server),
облачный API. `aitc` ничего не знает о модели — только дёргает `generate`.

> Референсный llama.cpp-адаптер живёт в исходном проекте SmartStock
> (`AIWrapper`): загрузка gguf, выбор CPU/GPU, выгрузка по простою, бюджет
> токенов под модель. Здесь его нет намеренно — ядро остаётся model-agnostic.

## 3. Запустить агента

```cpp
LlamaGenerator gen("model.gguf");
aitc::AgentResult r = aitc::runAgent(gen, reg, "Какая погода в Париже?", /*maxRounds=*/4);

std::cout << r.answer;        // финальный текст
for (auto& c : r.calls)       // что было вызвано — для логов/аудита
    log(c.tool, c.args.dump());
```

Что делает `runAgent`:
1. Собирает системный промпт из твоего реестра (`systemPrompt(reg)`).
2. Зовёт `gen.generate(...)`, снимает `<think>…</think>`, разбирает план вызовов.
3. Если план есть — **сам** исполняет каждый вызов через реестр и возвращает
   результаты модели; повторяет (до `maxRounds`).
4. Если плана нет — это финальный ответ, возвращает его.

Модель **никогда** ничего не исполняет сама — только предлагает; исполняет твой код.

## Тонкости

- **maxRounds** — потолок раундов генерации (защита от зацикливания). 3–4 обычно хватает.
- **Системный промпт** generic. Нужен свой стиль/язык — собери промпт сам и используй
  `parsePlan`/`splitThinking`/`reg.execute` как кирпичи (агент-цикл из ~30 строк, см.
  `runAgent` в `aitc.hpp`).
- **Парсер можно звать отдельно**: `aitc::parsePlan(text)` → `vector<ToolCall>` —
  если у тебя свой цикл общения с моделью.
