# Архитектура aitc

## Две роли, две абстракции

`aitc` разделяет «мозг» и «движок» — и обе вещи приносит пользователь:

```
        ┌──────────────────────── aitc (это ядро) ────────────────────────┐
        │                                                                  │
  вопрос│   systemPrompt(reg) ─► IGenerator.generate ─► splitThinking ─►   │
   ─────┼─►                                                  parsePlan     │
        │                                                       │          │
        │                                    план пуст? ─да─► финальный ответ
        │                                       │нет                       │
        │                          ToolRegistry.execute(call) ◄────────────┤
        │                                       │ (исполняет ТВОЙ колбэк)  │
        │                          результаты ─► в следующий промпт ───────┘
        └──────────────────────────────────────────────────────────────────┘
              ▲                                          ▲
       IGenerator (твоя модель)              ToolRegistry (твои инструменты)
```

- **`IGenerator`** — движок: `prompt → completion`. llama.cpp, HTTP, что угодно.
- **`ToolRegistry`** — мозг предметной области: твои инструменты как колбэки.
- **`aitc`** — клей между ними: промпт, парсинг, агент-цикл. Без предметных знаний.

## Почему план-протокол, а не «модель сама вызывает функции»

Слабые локальные модели (3–8B) при «нативном» tool-calling **конфабулируют**:
выдумывают несуществующие инструменты, подставляют выдуманные числа, путают
аргументы. Поэтому `aitc` по умолчанию использует **план-протокол**:

1. Модель отдаёт **JSON-план** вызовов — и больше ничего.
2. **Детерминированный код** (`runAgent`) исполняет план против **авторитетного
   реестра** — несуществующий инструмент не выполнится, числа берутся только из
   результатов.
3. Результаты возвращаются модели; она формулирует ответ из ФАКТОВ, а не из памяти.

Это смещает «творчество» модели туда, где оно безопасно (формулировка ответа), и
убирает оттуда, где оно вредит (доступ к данным). Подтверждено бенчем — см.
[`RESEARCH.md`](RESEARCH.md).

## Терпимый парсер

Главная практическая боль локальных моделей — **формат вывода пляшет**. `parsePlan`
тащит весь зоопарк одной функцией:

- массив `[{…}]`, обёртка `{"plan":[…]}`, одиночный объект `{…}`;
- ключи имени `tool` ИЛИ `name`; ключи аргументов `args|arguments|parameters|params`;
- JSON, утопленный в прозу («Sure, I'll call: […]») — скан сбалансированных литералов;
- скобки внутри строк не ломают баланс (учёт экранирования);
- лёгкий **ремонт** битого JSON: лишняя кавычка после числа (`{"limit":3"}`),
  хвостовая запятая (`{"a":1,}`) — частые ошибки мелких моделей.

Парсер — чистая функция над строкой, без модели и без сети, поэтому полностью
покрыт юнит-тестами.

## Границы (что НЕ входит намеренно)

- **Модель** — приносишь сам (`IGenerator`). Ядро model-agnostic.
- **Инструменты** — твои; ядро не знает ни про какую предметную область.
- **Выбор протокола под конкретную модель** — забота приложения. Ядро даёт сам
  набор протоколов (`ToolProtocol`) и разбор, но не маппит id модели на протокол,
  не переключает наборы инструментов по «силе» модели и не проверяет числа ответа
  на доменную привязку (для этого нужен предметный контекст) — это app-level.

## Нативные tool-протоколы

Кроме дефолтного план-протокола ядро умеет РОДНЫЕ форматы семейств
(`enum class ToolProtocol`): `PlanJson` (дефолт), `LfmPython`, `Hammer`, `Mistral`,
`Llama`, `Hermes`. `runAgent(gen, reg, q, maxRounds, protocol, cancelled)` принимает
протокол (по умолчанию `PlanJson` — обратная совместимость):

- **`systemPrompt(reg, protocol)`** строит скаффолдинг под формат, на котором семейство
  ОБУЧЕНО: Hermes — функции в `<tools>`, вызовы в `<tool_call>`; Mistral —
  `[AVAILABLE_TOOLS]`/`[TOOL_CALLS]`; Llama — `Environment: ipython` + JSON
  `{"name","parameters"}`; Hammer — секции `[BEGIN OF …]` + JSON-список; LfmPython —
  питонический список между `<|tool_call_start|>`/`<|tool_call_end|>`. `PlanJson`
  делегирует модель-агностик промпту.
- **`parseToolCalls(out, protocol)`** — диспетч разбора: `LfmPython` → `parsePyToolCalls`
  (чистый строковый разбор `[func(arg="x")]`, без Python); остальные → `parsePlan`
  (терпимо тащит JSON из `[TOOL_CALLS]`/`<tool_call>`/`{"name","parameters"}`) с
  питоническим фолбэком (ловит Llama 3.2, шлющую python-стиль под JSON-протоколом).

Устойчивость агент-цикла (`runAgent`): опциональный предикат **отмены** (`cancelled`,
проверяется после генерации и после каждого вызова); общий потолок вызовов
**`kMaxToolCalls`** (=8) поверх `maxRounds`; **кэш** результатов на запрос (один и тот же
`(tool, args)` не исполняется дважды); **клиппинг** длинного результата (UTF-8-safe,
~1800 байт) перед возвратом модели; **фильтр неизвестных** инструментов (`reg.has`);
одноразовый **retry** с фидбэком, когда модель явно пыталась вызвать инструмент, но
формат не разобрался; **`sanitizeAnswer`** снимает протёкшие chat-template токены
(`<|im_start|>`, `<|eot_id|>`, `<|tool_call_end|>` …) и заборы ``` из финального ответа.

> Заметка про KV-кэш: апстрим-движок на шагах >0 подаёт только приращение (флаг
> `firstStep`), чтобы llama переиспользовала KV-кэш. `IGenerator::generate` берёт полный
> промпт без инкрементального хука, поэтому `aitc` пересылает растущий промпт каждый
> раунд; адаптер с кэшем может опираться на общий префикс. Оставлено заметкой, API не
> сломан.

Свой протокол по-прежнему собирается из кирпичей (`parsePlan`, `parsePyToolCalls`,
`splitThinking`, `sanitizeAnswer`, `reg.execute`).
