## TL;DR

Я пилю SmartStock — складскую ERP, которая работает офлайн на каждой кассе/ПК и
синхронизируется через сервер, когда есть сеть. По дороге накопилось несколько
самостоятельных движков, и я вынес их в опенсорс под MIT:

- **sync-engine** — обнаружение конкурентных правок через vector clocks и разделение
  конфликтов на два типа с *разным* разрешением;
- **installer-glue** — персональный установщик за миллисекунды «склейкой» байтов, без перекомпиляции;
- **writeoff-engine** — партионный учёт FIFO/LIFO/средневзвешенная, без привязки к БД;
- **marketplace-adapters** — выгрузка остатков/цен и импорт заказов WB/Ozon/Yandex/Sber;
- **messenger** — самостоятельный E2E-мессенджер (веб + нативный Qt), один формат шифрования на обе платформы.

Ссылка на репозиторий: 〔ссылка на GitHub〕. Дальше — про то, что мне самому
показалось неочевидным: как мирить правки, которые сделали два человека офлайн.

## Откуда задача

Представь сеть маленьких магазинов/складов. Интернет есть не всегда, а работать надо
всегда. Поэтому в SmartStock **главный — десктоп**: он держит локальную SQLite и
полностью работает без сети. Появилась сеть — обменялся операциями с сервером.

Звучит просто, пока два человека офлайн не трогают одно и то же. Классика:

- ПК-A и ПК-B оба офлайн. На складе было **50** единиц товара.
- A продал **30**, B продал **30**. Каждый у себя прав: остаток позволял.
- Сеть вернулась. Сервер получает **обе** операции. Итог должен быть… какой?

И второй случай:

- A поменял цену товара на **80 ₽**, B — на **85 ₽**, оба офлайн.
- Чья цена «правильная»?

Я не сразу понял, что **это два РАЗНЫХ конфликта**, и лечить их надо по-разному.
Вот это и есть главная мысль статьи.

## Шаг 1. Как вообще понять, что правки конкурентны

Нельзя доверять системным часам разных ПК (их переводят, они врут, часовые пояса).
Поэтому «кто раньше» по времени — плохая идея. Нужны **vector clocks**.

Вектор часов — это просто `deviceId → счётчик`. Каждое устройство увеличивает
**свой** компонент при локальной записи. Сравнивая два вектора, можно понять
причинно-следственную связь: одна правка «знала» о другой (потомок) или они
сделаны параллельно (обе офлайн → конкурентны).

```ts
export type VectorClock = Record<string, number>;

// a доминирует над b (a — потомок b): для всех компонент a[k] >= b[k].
// Значит, a «видел» всё, что видел b → конфликта нет, a новее.
export function dominates(a: VectorClock, b: VectorClock): boolean {
  for (const k of Object.keys(b)) {
    if ((a[k] ?? 0) < (b[k] ?? 0)) return false;
  }
  return true;
}

// Конкурентны: никто не доминирует — правки «параллельны» (был офлайн).
// Это и есть ключевой признак смыслового конфликта.
export function isConcurrent(a: VectorClock, b: VectorClock): boolean {
  return !dominates(a, b) && !dominates(b, a);
}
```

`increment` (перед своей записью) и `merge` (покомпонентный максимум, когда узнал о
чужих операциях) — стандартные хелперы. Весь файл — 50 строк, без зависимостей.

> Важно: vector clock говорит только «параллельно или нет». Он **не** решает, кто
> прав. Это следующий шаг — и он зависит от того, ЧТО именно конфликтует.

## Шаг 2. Два типа конфликтов

### Физический конфликт: остаток ушёл в минус

Вернёмся к 50 единицам и двум списаниям по 30. Сервер применяет журнал операций
по порядку. Первое списание −30 → остаток 20. Второе −30 → **не хватает 10**.

Тут меня и осенило: **голосовать тут не за что**. Оба продавца реально продали
товар. Ни один не «неправ». Это не спор о данных — это расхождение учёта с
реальностью. Значит, списываем сколько было, а разницу фиксируем как **недостачу**
и просим инвентаризацию:

```ts
export function classifyPhysical(input: PhysicalInput): PhysicalOutcome {
  const available = Math.max(0, input.available);
  const writeoff = Math.min(input.requested, available);
  const shortage = input.requested - writeoff;
  if (shortage > EPS) {
    // Списали сколько есть, остаток — недостача (нужна инвентаризация).
    return { kind: 'physical_conflict', writeoff, shortage, available };
  }
  return { kind: 'applied', writeoff };
}
```

Никаких диалогов «выберите верную версию». Система просто честно говорит: «вот
здесь −10, сходите пересчитайте». Это оказалось гораздо ближе к тому, как реально
работают на складе, чем «давайте проголосуем, был ли товар».

### Смысловой конфликт: 80 ₽ против 85 ₽

А вот цена — другое дело. Тут нет «факта», есть **два мнения об одном поле**, и они
конкурентны по vector clock. Здесь уже нужно решение людей:

```ts
export function classifySemantic(input: SemanticInput): FieldVerdict {
  if (input.last === null) return FieldVerdict.Apply;       // первая правка поля
  const { incoming, last } = input;
  if (dominates(incoming, last)) return FieldVerdict.Apply; // входящая новее
  if (dominates(last, incoming) && !isConcurrent(incoming, last)) {
    return FieldVerdict.Stale;                              // входящая устарела
  }
  return FieldVerdict.Concurrent;                           // → голосование
}
```

При `Concurrent` поле **замораживается** (видны оба варианта, править нельзя) и
открывается голосование среди тех, у кого есть право на эту сущность. Большинство
при полном кворуме → автоматически в БД:

```ts
export function tallyVote(t: VoteTally): VoteResolution {
  if (t.cast >= t.eligible && t.a !== t.b) {
    return { resolved: true, winner: t.a > t.b ? 'a' : 'b', mode: 'majority' };
  }
  return { resolved: false };
}
```

Равенство или дедлайн — решает админ, он же может закрыть досрочно (вето). Один
голос на человека.

### Зачем это разделение

Если валить всё в один механизм, получается плохо в обе стороны:

- голосовать за физический остаток — абсурд (товар или есть, или нет);
- молча перезаписывать цену «последним пришёл» — теряешь чужое решение и злишь людей.

Разделив на «факт» и «мнение», каждый случай лечится естественно. Для меня это было
главным инсайтом всего проекта: **сначала спроси, что за сущность конфликтует, и
только потом выбирай стратегию.**

## Бонус-хак: персональный установщик за миллисекунды (без перекомпиляции)

Вторая штука, которой я горжусь, — `installer-glue`. Проблема: на каждого
пользователя нужен свой установщик (адрес сервера, токен привязки, логин, роль,
какие вкладки включены, логотип, шаблоны печати). Пересобирать приложение под
каждого — это Qt/MSVC, тяжёлый CI, минуты времени. Это безумие при создании учётки.

Решение: базовый `SmartStock-base.exe` собирается **один раз** и содержит все
модули. А сервер просто **дописывает в конец бинаря хвост** — и всё:

```
[оригинальный exe]
[MAGIC            : 8 байт  = "SMSTOCK1"]
[manifest length  : uint32 LE]
[manifest.json    : UTF-8]                ← serverUrl, токен, роль, флаги вкладок…
[файлы…]          : имя+данные (логотип, лицензия, шаблоны)
[FOOTER : 24 байта]:
    [magic offset : uint64 LE — где начинается хвост = размер базового exe]
    [CRC32        : uint32 LE — zlib-совместимый]
    [file count   : uint32 LE]
    [MAGIC        : 8 байт — повтор "SMSTOCK1"]
```

Почему это вообще работает: лишние байты **после** полезной нагрузки PE/ELF (и APK)
загрузчик просто игнорирует — exe остаётся валидным и запускается. При первом старте
приложение читает **свой собственный** бинарь с конца: последние 24 байта — FOOTER,
по `magic offset` находит хвост, проверяет MAGIC и CRC32, разбирает манифест.

Отдельно порадовало, что CRC32 здесь **zlib-совместимый** (`node:zlib`), поэтому
нативный ридер на C++ (`zlib::crc32`) валидирует ровно те же байты, что и Node-сборщик.
Один формат — две реализации, и они сходятся.

Итог: персональный установщик собирается **за миллисекунды на любой ОС без тулчейна**.
Тот же приём работает для APK. Один бинарник для всех — отличается только вшитый хвост.

```bash
installer-glue append \
  --base SmartStock-base.exe \
  --manifest manifest.json \
  --file logo.png=./assets/logo.png \
  --out SmartStock-user42.exe
```

## Что ещё в репозитории

- **writeoff-engine** — партионный учёт (FIFO/LIFO/средневзвешенная), резервы,
  возвраты. Алгоритм отделён от хранилища интерфейсом `BatchStore` — подключаешь
  свою БД. 14/14 тестов. Есть и C++-оригинал в `cpp-reference/`.
- **marketplace-adapters** — FBS-адаптеры WB/Ozon/Yandex/Sber: остатки, цены,
  импорт заказов. HTTP-клиент инъектируется, ключи продавца библиотека не хранит.
  Zero runtime deps, 23/23 теста.
- **messenger** — самостоятельный E2E-мессенджер: сервер + веб-клиент + нативный
  Qt-клиент, группы и файлы. Один формат `crypto_box`/`secretbox` работает и в
  вебе (tweetnacl), и в Qt (libsodium); приватный ключ не покидает устройство.

Каждый модуль автономен, со своим README, тестами и MIT.
