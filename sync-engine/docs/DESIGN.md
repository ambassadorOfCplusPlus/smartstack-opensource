# Offline-first event sync — справочный дизайн

Это разбор архитектуры офлайн-первой синхронизации, извлечённой из SmartStock
(рой десктопов с локальной SQLite + узел синхронизации на Node.js/PostgreSQL).
Документ написан как **дизайн для переиспользования**, а не как реклама: каждое
утверждение соответствует исходному коду в [`../reference/server`](../reference/server),
а чистое ядро — в [`../src`](../src).

Сценарий: десктопы работают **офлайн**, накапливают локальные изменения и при
появлении сети синхронизируются через сервер. Часам клиентских ПК доверять
нельзя, сеть теряет ответы, два ПК могут править одно и то же независимо. Дизайн
обязан быть корректным при всех трёх условиях.

---

## 1. Модель: синхронизируем СОБЫТИЯ, а не состояние

Мы НЕ синхронизируем «остаток = 50». Мы синхронизируем **журнал операций**:
приход +100, списание −30. Сервер применяет операции по порядку и сам считает
итог. Почему так:

- Состояние («остаток 50») при слиянии двух офлайн-копий теряет информацию: чьё
  «50» правильное? События складываются естественно: +100 и −30 с двух ПК дают
  детерминированный итог независимо от порядка доставки.
- Каждая операция несёт `id` (UUID, генерирует **десктоп**), `deviceId`,
  `vectorClock`, `createdAt` (время ПК — только для UX, не для порядка).

Контракт операции (см. `reference/server/types.ts`):

```ts
interface SyncOperation {
  id: string;            // UUID, генерирует десктоп — КЛЮЧ ИДЕМПОТЕНТНОСТИ
  entityType: 'batch' | 'product';
  entityId: string;      // UUID партии или товара
  operation: 'batch_receipt' | 'batch_writeoff' | 'product_update';
  payload: ...;          // зависит от operation
  vectorClock: Record<string, number>; // deviceId → счётчик
  createdAt: string;     // ISO, время на ПК (НЕ источник порядка)
}
```

Принципиальные решения контракта:

- **Списание привязано к КОНКРЕТНОЙ партии по `batchId`**, а не FIFO-подбор.
  FIFO недетерминирован при слиянии (порядок доставки разный на разных узлах);
  явная привязка к партии делает применение детерминированным.
- **Порядок задаёт сервер**, а не часы ПК: серверный `serverSeq` (autoincrement)
  + `vectorClock` для причинности. Часам ПК не доверяем вообще.

## 2. Поверхность API

```
POST /sync/push                 — принять пачку операций, слить, детектировать конфликты
GET  /sync/pull?since=&deviceId= — отдать ЧУЖИЕ операции (serverSeq > since, deviceId != свой)
GET  /sync/snapshot?warehouseId= — полный снимок склада для первой синхронизации ПК
POST /conflicts/:id/vote        — голос в смысловом конфликте
POST /sync/resolve-conflict     — решение конфликта админом (большинство / вето)
```

- **push** — пачкой (до 1000 операций). Каждая операция валидируется и
  применяется **по отдельности** в своей транзакции: одна кривая операция не
  роняет всю пачку (частичный успех допустим). Ответ — `{ accepted, conflicts,
  rejected, maxServerSeq }`.
- **pull** — пагинированная выдача чужих операций по возрастанию `serverSeq`.
  Курсор `since` десктоп двигает по последнему полученному `serverSeq`.
- **snapshot** — для нового ПК: полный список товаров/партий/ячеек склада +
  `lastSeq` (с какого `serverSeq` начинать pull). Дальше ПК живёт инкрементально.

## 3. Идемпотентность по UUID

`id` операции генерирует десктоп ОДИН раз. Сеть может потерять ответ на push, и
десктоп повторит ту же пачку — сервер обязан **не задвоить** эффект.

Алгоритм (см. `service.ts: push` и `src/journal.ts: append`):

1. На каждую операцию — `findUnique` по `id` в `sync_operations`.
2. Если запись есть — операция уже принята: **не применяем повторно**, возвращаем
   её сохранённый статус и `serverSeq` (через `classifyKnown`).
3. Иначе применяем и записываем с новым `serverSeq`.

Гонка двух одновременных push с одним `id`: между `findUnique` и `create` второй
получит `P2002` (нарушение уникальности PK). Это НЕ ошибка — это «уже принято»:
перечитываем запись и возвращаем её фактический статус. То есть идемпотентность
держится и под конкуренцией, опираясь на уникальный первичный ключ, а не только
на проверку-перед-вставкой.

В `src/journal.ts` это показано в чистом виде: `append(op)` для известного `id`
возвращает `{ duplicate: true, entry }` с тем же `serverSeq`, и `maxSeq()` не
растёт.

## 4. Vector clocks — детекция конкуррентности

Вектор часов: `deviceId → счётчик`. Устройство инкрементирует свой компонент при
локальной записи. Сравнение двух векторов даёт причинность (см.
`src/vector-clock.ts`, скопировано вербатим из `conflict.service.ts`):

```ts
// a доминирует над b: для всех k, a[k] >= b[k] (a «видел» всё, что b)
function dominates(a, b) {
  for (const k of Object.keys(b)) if ((a[k] ?? 0) < (b[k] ?? 0)) return false;
  return true;
}
// конкуррентны: никто не доминирует (правки параллельны — был офлайн)
function isConcurrent(a, b) {
  return !dominates(a, b) && !dominates(b, a);
}
```

Как это используется при `product_update` (см. `service.ts:
classifyProductUpdate`, чистая версия — `src/conflict.ts: classifySemantic`):

- последней принятой правки этого поля нет → `apply` (первая правка);
- входящая доминирует над последней → `apply` (входящая новее, видела прошлую);
- последняя доминирует над входящей (и не конкуррентны) → `stale`: правка
  устарела, тихо игнорируем (десктоп получит актуальное значение по pull);
- иначе `isConcurrent` → **смысловой конфликт**, открываем голосование.

Важная деталь из боевого кода: «последняя правка поля» ищется фильтром именно по
этому полю (`payload.path:['field']`), а не «последние N операций товара» — иначе
окно из правок ДРУГИХ полей могло бы скрыть истинную последнюю правку и ложно
вернуть `apply`, не заметив конфликт.

## 5. Gap-free pull через xmin-горизонт — тонкая часть

Это самое неочевидное место всего дизайна. Цитируется по комментариям в
`service.ts` (`pullSafetyMs`, `safeHorizonSeq`).

### Проблема

`serverSeq` — это autoincrement, который PostgreSQL присваивает **в момент
INSERT**. Но строка становится **видимой** другим читателям только **после
COMMIT** её транзакции. Под конкуренцией это расходится:

```
T1 начинает, INSERT → serverSeq = 100   (ещё не закоммичена, НЕВИДИМА)
T2 начинает, INSERT → serverSeq = 101
T2 COMMIT                                 (101 теперь ВИДИМА)
   ← в этот момент десктоп делает pull
T1 COMMIT                                 (100 становится видимой ПОЗЖЕ 101)
```

Наивный курсор `serverSeq > since`: десктоп на pull видит 101, продвигает
`since := 101`. Операция 100 закоммитилась позже, но её `serverSeq` уже **меньше**
курсора — следующий pull (`serverSeq > 101`) её **никогда не вернёт**. Операция
теряется навсегда, рой десктопов молча расходится с сервером по остаткам. Это не
гонка с малой вероятностью — это системный пропуск.

### Решение: горизонт видимости (xmin)

Отдавать на pull только строки, **видимые всем активным транзакциям** — те, чей
`xmin` (id транзакции, создавшей строку) старше горизонта снапшота. Если строка
видна всем, ни одна in-flight транзакция уже не сможет закоммитить позже видимую
строку с меньшим/равным `serverSeq`. Горизонт = `pg_snapshot_xmin` текущего
снапшота: самая старая ещё-не-завершённая транзакция. Курсор продвигается только
до этого горизонта.

Запрос из `service.ts: safeHorizonSeq` (потолок `serverSeq` для pull/snapshot):

```sql
SELECT max(server_seq)::text AS seq FROM sync_operations
WHERE organization_id = $1::uuid AND status = 'accepted'
  AND age(xmin) > age(pg_snapshot_xmin(pg_current_snapshot())::text::xid)
```

Тонкости, найденные на боевом тесте (тоже в комментариях исходника):

- `pg_snapshot_xmin(pg_current_snapshot())` возвращает `xid8` (64-бит), а `age()`
  принимает только 32-бит `xid`. Без каста `::text::xid` PostgreSQL бросает
  `function age(xid8) does not exist`, и горизонт **молча** деградирует в
  fallback — fake-БД в юнит-тестах этот баг не ловила, поймал live-тест.
- Сравнение через `age()` иммунно к wraparound id транзакций.
- На pull курсор ограничивается `serverSeq <= horizon`; `snapshot.lastSeq` тоже
  считается с тем же горизонтом (иначе первая синхронизация ПК перепрыгнула бы
  невидимую операцию).

### Fallback

Где `$queryRaw`/xmin недоступны (не-Postgres, фейк-Prisma в тестах) —
эвристическое **окно `pullSafetyMs`**: отдаём только операции, чьё время старта
транзакции старше окна. Это best-effort, а не гарантия: оно надёжно, только если
транзакция коммитится быстрее окна; транзакция, живущая дольше окна, его обходит.
В проде истину даёт именно xmin-горизонт, окно — деградация.

> В `src/journal.ts` этот эффект **не** воспроизводится: in-memory журнал
> синхронен, параллельных коммитов нет, поэтому курсор `serverSeq > since` там
> тривиально gap-free. Феномен существует только в реальной СУБД с MVCC.

## 6. Два типа конфликтов

### Физический (остаток ушёл бы в минус)

Два ПК офлайн списали 30 и 30, а было 50. **Оба списания валидны** — товар
физически выдан. Спорить не о чем, голосование не нужно: это расхождение учёта с
реальностью.

Поведение (см. `merge.service.ts: applyBatchWriteoff`, чистая версия
`src/conflict.ts: classifyPhysical`):

- списываем `min(requested, available)` с указанной партии (частичное списание
  допустимо), разницу возвращаем как `shortage`;
- фиксируем **недостачу** и шлём уведомление «нужна инвентаризация» админам и
  кладовщикам (и отдельно бухгалтерам — со ссылкой на журнал действий товара),
  см. `conflict.service.ts: notifyPhysicalShortage`;
- операция записывается со `status='conflict'`, итог склада остаётся
  непротиворечивым (в минус не уходит).

### Смысловой (конкуррентная правка одного поля)

Цена 80₽ на ПК-A и 85₽ на ПК-B, оба офлайн → `isConcurrent` (см. §4). Здесь
правильный вариант выбирают **люди**:

- поле **замораживается**: пока идёт голосование, любая правка этого поля
  отклоняется со статусом `frozen` (`merge.service.ts: applyProductUpdate`
  проверяет открытое голосование);
- открывается голосование (`ConflictVote`) с `optionA` (текущее серверное
  значение) и `optionB` (входящее), дедлайн по умолчанию 24 ч;
- голосуют пользователи **с правом на сущность** (`products:edit`), **один голос
  на человека** (составной PK `conflictId+userId`; гонка двойного голоса →
  `P2002` → «уже проголосовал», а не 500);
- **авторазрешение**: как только проголосовали все правомочные и есть перевес —
  большинство применяется (`src/conflict.ts: tallyVote`);
- **равенство/дедлайн → решает админ**; админ может закрыть досрочно (**вето**) —
  `src/conflict.ts: resolveByAdmin`, в боевом коде `ConflictService.resolve`;
- по дедлайну (`checkDeadlines`, из cron/worker) просроченные голосования →
  уведомление админам «решение за вами».

Замороженная операция намеренно **НЕ** записывается в `sync_operations` как
терминальная (см. большой комментарий в `service.ts: applyAndRecord`): иначе
идемпотентный повтор после resolve нашёл бы её как `accepted` и вернул бы
`accepted` БЕЗ применения — правка потерялась бы. Не записав её, мы даём десктопу
повторить push после разморозки, и операция переоценивается заново
(`apply` / `stale` / снова `concurrent`).
